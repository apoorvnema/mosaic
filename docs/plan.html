1 · Thesis and scope

Five apps, five habits. The reason people run all of them is that each one is uncompromising about a single thing, and each one is bad at the others.

The failure mode of "one app to replace them all" is a product that is mediocre at six jobs. Mosaic avoids that by picking one substrate that can genuinely express all of them: a block tree stored as plain files, merged by a CRDT, indexed by a local database. A quick note, a typed database row, a markdown document, a whiteboard shape and a sticky note on your desktop are all the same object, rendered by a different view.

That single decision is what makes the rest of this plan possible. It is also the main technical risk, so it is validated in the first eight weeks before anything is built on top of it.

Non-negotiable one

Capture is instant and offline. Hotkey to typed text in under 400 ms, cold, with no account required.

Non-negotiable two

Your notes are files. Delete the app, keep the folder. Markdown, images, JSON canvases — readable in any editor.

Non-negotiable three

Structure is optional and additive. Typed fields never block you from writing a messy note.

In scope for 1.0

  • Desktop: Linux, Windows, macOS. Mobile: Android, iOS. Web: PWA. macOS and iOS in the last phase
  • Accounts, multi-device sync, an encrypted vault, sharing by link.
  • Markdown notes, typed collections and views, infinite canvas with ink, Mermaid, Excalidraw-compatible drawings, sticky notes pinned in-app and on the OS.
  • A plugin runtime, a theme system, and importers from Keep, Notion, Obsidian, OneNote and Evernote.

4 · System overview

One core library written once, wrapped in a thin shell per platform. The shells own windows, widgets, pens and permissions. The core owns everything that could ever disagree between devices.

Why one core

Sync, merge, validation, search and encryption are the parts where a bug means lost or corrupted notes. Writing them once in a memory-safe language and running the exact same compiled logic on every platform is the difference between one hard problem and six subtly different ones. The shells then only handle what is genuinely native: windowing, widgets, pen events, notifications, file pickers, biometrics.

5 · Stack decision

Scored against the constraints that actually bind this product: a rich text and canvas editor, a JavaScript plugin ecosystem, six targets, and a small team.

Decision

Rust core exposed three ways — a native library for desktop, UniFFI bindings for Android and iOS, and a WebAssembly build for the browser — with a single TypeScript and React interface shipped inside Tauri v2 on all five app targets and served directly on the web. If Rust is not on the team, section 5 sets out the same architecture in TypeScript — the shape survives the language change.

Component choices

  • Editor: a block editor built on ProseMirror, with a markdown serializer that round-trips losslessly. Not a from-scratch contenteditable.
  • CRDT: Loro or Yjs, decided by the week-6 spike; both give sequence CRDTs for text and maps for properties, with binary updates.
  • Local index: SQLite with FTS5, plus Tantivy if ranking quality demands it.
  • Canvas: custom scene graph over WebGL2 with a WebGPU path where available; tiled rendering and a separate low-latency ink layer.
  • Backend: Rust with axum, Postgres, Redis, S3-compatible object storage.
Known weak point

Tauri v2 mobile is younger than the desktop story, and pen latency inside a WebView is the single riskiest assumption in this stack. Phase 0 includes a measured spike on a mid-range Android tablet with a stylus. If latency exceeds 40 ms after prediction, the ink surface — and only the ink surface — becomes a native view composited under the WebView, which is scoped at three weeks.

6 · Building this without Rust

The Rust core in section 5 is an optimisation, not a requirement. Obsidian, Notion, Affine, Excalidraw and tldraw are all TypeScript products. If Rust is not on the team, the architecture survives intact — only the implementation language of the core changes.

Note that Tauri does not require you to write Rust. The shell is scaffolded for you; touching it means adding a plugin or a command, which is a few lines each time. Path B can keep Tauri and its small binaries without learning the language.

What Path B actually costs

  • Large vaults. Indexing 10,000 notes in JavaScript is fine if it happens in a worker against SQLite full-text search, and painful if it happens on the main thread. This is an architecture decision on day one, not a tuning exercise later.
  • Memory and battery on mobile. A WebView core costs more of both. It shows up as background sync being killed by the OS sooner, so schedule sync work rather than holding a socket open.
  • Ink latency. The riskiest item, and it is risky on both paths — the ink surface may end up native regardless. Budget the same three-week fallback.
  • Plugin sandboxing. Without a WebAssembly host boundary you rely on iframes and workers with a message port. Workable and widely used, but the capability model has to be enforced by the host rather than the runtime.
  • Merge correctness at scale. Yjs is mature and battle-tested, so this is the least worrying item. Document sizes above a few megabytes want snapshotting either way.
Keep the door open

Put the core behind a narrow interface from the first commit — store, merge, index, crypto, ink — with no framework types crossing it. Only three of those ever justify being rewritten in Rust or WebAssembly: the search index, the ink pipeline, and the file diff and merge. Everything else stays TypeScript forever. That turns "we chose wrong" into a two-week port of one module rather than a rewrite.

Choose Path B if

You are one to three people, TypeScript is your strongest language, and getting to a usable app in month five matters more than the last twenty percent of performance. This is the right answer for most people reading this.

Choose Path A if

You are hiring to six or more, at least one person has shipped production Rust, and you expect vaults in the tens of thousands of notes with heavy ink from day one. Or you hire one Rust engineer for the core only and own the interface yourself.

If you want to learn Rust on this project anyway, do not learn it on the sync engine or the crypto — those are the two places where a beginner's mistake silently destroys someone's notes. Port the search indexer first: self-contained, easy to test against the TypeScript version, and the speedup is measurable. Realistically you are two or three months from being productive, which is roughly the whole of phase 0 and phase 1.

Schedule impact: Path B reaches M1 about a month sooner and may spend that month back around M3 if the canvas hits a performance wall. The eighteen-month shape in section 20 holds on either path.

7 · Data model

Files are what you own. Blocks are what the app edits. The index is disposable. Keeping those three roles straight is what lets Obsidian-style freedom and Notion-style structure exist in one product.

The folder

Point Mosaic at an existing Obsidian folder and it works, because that folder already is the format. Everything Mosaic adds beyond markdown lives in frontmatter or in the hidden directory, so another editor sees ordinary files.

Blocks

A note is an ordered tree of blocks. Every block carries a stable identifier, a type, content, and optional properties. Stable ids are what make block links, transclusion, per-block history and fine-grained merging possible; they are stored as an unobtrusive trailing anchor in markdown and are only materialised for blocks that something actually references.

Typed collections — the Notion half

A collection is a schema file that claims a folder or a query. It declares fields with types: text, number, date, select, multi-select, checkbox, url, relation, rollup, formula. Note properties live in YAML frontmatter, which stays human-readable and diff-friendly.

  • Validation on write. Typing a word into a number field is refused in the editor, the way a database column would refuse it.
  • Repair, never destroy. If a file is edited outside Mosaic and violates the schema, the value is preserved verbatim and flagged in a repair queue. Structure never justifies deleting what you wrote.
  • Views are queries. Table, board, calendar, gallery and list are saved queries with a layout, computed from the SQLite index. A note can appear in many views and belongs to none of them.
  • Relations are links plus an index; rollups and formulas are evaluated in the core so every platform agrees on the result.

Search and links

The index holds full text, block metadata, properties, tags, outbound and inbound links, and canvas object positions. It is derived: deleting it costs a rebuild and nothing else. That rule is enforced by a nightly test that wipes the index and asserts the app is byte-identical afterwards.

8 · Sync engine

Local-first. Every device holds a complete replica, edits apply immediately, and the network is an optimisation. The server stores opaque updates and never has to understand a note.

How merging works

  • Text uses a sequence CRDT, so two people typing in the same paragraph converge without a conflict dialog.
  • Properties use a last-writer-wins register per field, with typed coercion — the loser is kept in history, not discarded.
  • Canvas objects use a map of shapes keyed by id; moves are last-writer-wins per object, so two people moving different shapes never collide.
  • Ink strokes are immutable once finished, which makes them trivially mergeable: a stroke is only ever added or removed.

The hard part: files and CRDTs at the same time

Two sources of change exist — the app, and whatever else touched the file. The file bridge handles it with a stored base version per file: on an external change, it diffs the file against the last known text, converts that diff into CRDT operations, and applies them as if a peer had made them. Ambiguity is surfaced once, in a banner offering both versions side by side, and the original file is always preserved in a timestamped copy first.

Version history

The update log is the history. Snapshots every few hundred updates keep loading fast; older updates compact into snapshots on a schedule with a retention window that is 30 days locally and configurable in the cloud. Restore works per note, per block, and per canvas object.

Attachments

Content-addressed by hash, deduplicated, uploaded separately from document updates with resumable transfers. Large media stays out of the CRDT log entirely — only the hash and metadata are synced.

9 · Accounts and auth

An account is optional until the second device. Everything works signed out, on one machine, forever.

  • Sign-in: passkeys first, with email and password as the fallback, plus Google, Apple and GitHub. Time-based codes and recovery codes for second factor on the password path.
  • Sessions: short-lived access tokens with rotating, device-bound refresh tokens. A device list in settings, each entry revocable, with the revocation taking effect on the relay within seconds.
  • Devices: each install generates a key pair on first run. New devices are approved by an existing device — a QR code or a six-digit code — which is also how encryption keys travel without ever reaching the server.
  • Critical separation: the sign-in credential is not the encryption key. This is what allows social sign-in to coexist with end-to-end encryption, and it is why a forgotten passphrase cannot be recovered by support.
  • Self-hosting: a single binary plus Postgres and an S3-compatible bucket. Teams get OIDC and SCIM after 1.0.

10 · Vault and encryption

Two tiers, because "encrypted" and "the server literally cannot read it" are different promises and users deserve to know which one they have.

Tier one — account encryption

Everything synced is encrypted with an account key held on your devices. Convenient: unlocks with your session, works with link sharing and previews. The server stores ciphertext.

Tier two — the Vault

A separate passphrase, never sent anywhere, never held after lock. Unlocks with biometrics locally, auto-locks on a timer and on sleep. Vault notes are excluded from server-side features and from plugins unless explicitly granted.

Construction

  • Content encrypted with XChaCha20-Poly1305; a fresh data key per document, wrapped by the vault key.
  • Vault key derived with Argon2id, parameters tuned per device class and stored with the ciphertext.
  • Device-to-device key transfer over X25519, authenticated by the pairing code.
  • Recovery by a 24-word phrase generated at setup; optionally split into shares for people who want a safety net.
  • Attachment filenames and sizes padded into buckets, because file size is a leak.
  • Search inside the vault runs against a local-only index that is itself encrypted at rest.

What the server can still see

Visible to the serverNever visible
Account identity and billingNote text, titles, tags, properties
Document identifiers, sizes, update timingAttachment content and true filenames
Device list and IP addressesVault passphrase or any key derived from it
Sharing graph for shared documentsAnything inside the vault, under any circumstance

Stated plainly in the product too, on the screen where the vault is created. A security promise nobody understands is not a security feature.

The capture window is a separate lightweight process that starts with the OS and holds a pre-warmed editor. It writes straight to the log and returns; indexing, sync and file writing happen after the window is already closed.

Three meanings of "pinned"

  1. Pinned in the app — the note sits at the top of the board, exactly like Keep.
  2. Pinned to the desktop — a frameless, always-on-top window with a colored background, remembering position per monitor and per workspace. On Wayland this uses the layer-shell protocol, on X11 the older window manager hints, on Windows a tool window with a topmost flag.
  3. Pinned to the system — an Android home-screen widget or an ongoing notification, an iOS widget later. Editable in place where the platform allows it; tapping opens the same note, not a copy.

All three are flags on one note. A sticky is never a different object with its own storage, which is the mistake that makes other products' sticky notes a second, worse silo.

Screen-by-screen layout, widget sizes and the phone navigation model are in section 12.

Sticky window behaviour on the desktop

A sticky that is always in the way is as useless as one you can never find. Two controls solve that, and they are independent of each other.

The pin

  • A pin control in the corner of every sticky. Pinned means always on top of every other application, across workspaces.
  • Unpinned, it behaves as an ordinary window and falls behind whatever you are working in.
  • The state is stored on the note, so it survives a restart and applies to that sticky only.
  • A global shortcut summons every sticky to the front, and another hides them all — useful before screen sharing.

Auto-collapse

  • When the pointer leaves, the sticky rolls up to its title strip after a short delay, default 600 ms and adjustable.
  • Hovering over the strip peeks it back open where it sits; clicking pins it open until you click away.
  • It never collapses while the caret is in it, while text is selected, or while a drag is in progress. A note that swallows a half-typed sentence is worse than no note.
  • Collapsed appearance is configurable: title strip, a colour tab docked to a screen edge, or just a drop in opacity.
  • Optional click-through while collapsed, so a docked sticky never steals a click meant for the window behind it.
  • Focus-out collapses too, not only mouse-out, so the behaviour works for someone navigating by keyboard.
Platform caveat

Always-on-top and absolute window positioning are straightforward on Windows, macOS and X11. On Wayland they are not: compositors built on wlroots support the layer-shell protocol that this needs, while GNOME's does not expose it to ordinary applications. The fallback there is a normal always-on-top window without edge docking, and the setting is hidden rather than offered and broken. Worth confirming early if Linux is your main desktop.

12 · Mobile design

Two interfaces worth copying, and they disagree with each other. Keep is flat, instant and one screen deep. OneNote is a hierarchy you navigate. The phone app runs both, as two lenses on the same notes, and never as two stores.

How the two models coexist

Board is where notes land. Notebooks is where they live. A quick capture goes into an Inbox section and shows on the board; filing it into a notebook section takes it off the board without copying or moving anything the user can see. A filed note can still be pinned back to the board, because pinning is a flag rather than a location.

This lines up exactly with the file layout in section 7: a notebook is a top-level folder, a section is a subfolder, a page is a note file, the board is a saved query, and a sticky is a flag plus a colour. Neither view owns the data.

The Keep parts, kept

  • Two-column masonry, colour cards, checkbox previews and image thumbnails. Pinned notes in their own row above the rest.
  • A capture row fixed at the bottom of the board: text, checklist, ink, photo, voice — one tap each, no menu, all within thumb reach.
  • Long-press to multi-select, swipe to archive, and an undo that actually undoes.
  • Labels as chips in the drawer; one search field covering text, labels, and later ink.
  • The app opens on the board with content already drawn from local storage. No splash, no sync spinner, no modal that blocks writing.

The OneNote parts, kept

  • Breadcrumb plus a horizontal row of section chips, each carrying its colour, collapsible into the notebook list.
  • Section colour runs down the spine of every page row, which is what makes a long list scannable at a glance.
  • Swipe left and right to move between pages in a section, the way flipping through a notebook works.
  • Freeform pages open in a reflowed reading layout on a phone, with one toggle to the true canvas. Full freeform placement is a tablet and desktop affordance; pretending otherwise on a 6-inch screen helps nobody.
  • Sticky notes as a first-class surface rather than a separate app.

Tablet and pen

Two panes on a tablet — list and note — and three on a wide screen with the notebook tree pinned open. With a stylus detected the canvas goes full-bleed, palm rejection turns on, and the toolbar moves to the side the pen is not on. An attached keyboard enables the same shortcuts as desktop, including the capture hotkey.

Visual language

  • One card style everywhere. Elevation appears only on a pinned or dragging card, never as decoration.
  • Twelve note colours whose meaning is assigned by the user, stable across devices. Dynamic system colour is allowed for widget chrome only — the note colours themselves must not shift between a phone and a laptop.
  • Dark mode desaturates the note colours rather than inverting them, so a yellow note is still recognisably that note.
Mobile release-blocking

Board drawn from local storage in under 1.5 s cold. Widget tap to a typed character in under 400 ms. Capture, search and the note button all reachable one-handed. No dialog ever blocks writing — not for sync, not for sign-in, not for an update.

13 · Two workflows this has to nail

Features are only worth building if they compose into something you do every day. These two are the daily test: a project diary across several projects, and a bug table across several repos and devices. Both are built from the primitives already described — no new engine, no new store.

The daily journal

One page per day per project, created from a template, opened by a single shortcut. It is a collection with a date field, so the pages are ordinary markdown files that happen to be queryable.

The template

  • Deploying today — tasks with a target
  • Working on — what is actually in progress
  • Blocked — with the reason, so it reads back usefully
  • To discuss — the stand-up list
  • Done — filled as the day goes

The mechanics

  • One shortcut opens today's page for the active project, creating it if needed
  • Unticked tasks roll forward to tomorrow, marked with the date they came from
  • Completed items stay on the day they were finished
  • A widget tile goes straight to today's page
  • Per-project templates, so a backend project and a design project can differ

Because every line is a block with properties rather than loose text, the same entries can be read back in other shapes without being copied anywhere:

  • Stand-up view — yesterday, today and blockers side by side, across every project, generated at the moment you open it.
  • Week roll-up — every "to discuss" line from all projects in one page, exportable as a status report.
  • Calendar and streak — the journal as a month grid, with gaps visible.
  • Open across projects — a saved query of every unticked task, regardless of which day's page it was written on.

Mentioning a bug id, a repo or a person in a journal entry links it both ways, so a bug's page shows every day it was discussed without anyone maintaining that list.

The bug table

One project, several repositories, several devices. What is wanted is the ergonomics of a spreadsheet with the depth of a note behind each row, shareable without inviting anyone into a repo.

What the spreadsheet view does

  • Inline editing with full keyboard navigation — tab, enter, arrows, fill-down, multi-row select. It should feel like a spreadsheet, not a web form.
  • Sort, filter and group by any field. Group by repo for a release check, by device for a hardware pattern, by status for triage.
  • Saved views for the questions you ask repeatedly: open bugs on one repo, crashes on one device, fixed and awaiting verification.
  • A board view of the same rows grouped by status for triage, and a calendar by date found.
  • CSV import and export that round-trips, because the data probably starts in a spreadsheet and should be able to go back to one.

What a spreadsheet cannot do

  • Every row opens as a complete note: reproduction steps, pasted screenshots with ink annotation on top, attached logs, a recording.
  • Filing a bug from the phone captures device model, OS version and app build automatically.
  • Status history comes from the edit log, so time-in-status and time-to-fix need no extra tooling.
  • Share one view by link, read-only or with comments, with revocation — a tester can file and comment without an account in your code host.
  • Every row is a markdown file with frontmatter, so the whole tracker is greppable, diffable and yours.
Deliberately out of scope

Two-way synchronisation with GitHub, GitLab or Jira issues. It is the obvious next ask and it is a plugin, not core — the capability model in section 15 exists so that someone can build it without the tracker itself growing a dependency on anyone's API. A one-way export of selected rows to issues is a reasonable phase 5 addition.

14 · Canvas, ink and diagrams

One engine serves the infinite whiteboard, the OneNote-style freeform page, and the drawing embedded in a markdown note. Different bounds, same scene graph.

Rendering

  • Scene graph split into spatial tiles; only visible tiles rasterise. Boards of tens of thousands of objects stay at 60 frames per second.
  • An ink layer separate from the scene, drawn with the shortest possible path from pointer event to pixel, with motion prediction to hide the remaining latency.
  • Strokes captured with pressure, tilt and velocity, stored as compressed point arrays, fitted to curves on completion.
  • Palm rejection driven by pointer type and contact geometry; an explicit pen-only mode for tablets.
  • Shape recognition on a slow-drawn stroke, snapping, alignment guides, and connectors that stay attached when a shape moves.

Diagrams that stay yours

  • Mermaid blocks are text in the markdown file, rendered live. Edit as code or through a small form.
  • Drawings read and write the .excalidraw format, so the same file opens in Excalidraw. Import is not a one-way conversion.
  • Cards on a canvas are transclusions: the card shows a real note, and editing either place edits the same thing.
  • Export a board or a page to SVG, PNG or PDF, with vector text preserved.
Performance budget

Pen down to first ink under 30 ms on a mid-range Android tablet. Board pan and zoom at 60 fps with 10,000 objects. A board opens in under 800 ms cold. These are release-blocking numbers measured in continuous integration on real hardware, not aspirations.

15 · Plugins and themes

The reason Obsidian is sticky. Also the fastest way to lose control of security and performance, so the capability model comes before the first plugin ships.

  • Two runtimes. Compute plugins are WebAssembly components with a typed host interface — safe, fast, and identical on every platform. Interface plugins run in a sandboxed frame talking over a message port, which is what lets existing web-based tools be ported.
  • Capabilities are declared and shown. A manifest requests exactly what it needs: read notes matching a query, write to a folder, reach named network hosts, add a view. The install screen lists them in plain language. Nothing gets ambient access.
  • The vault is off by default and requires a separate, explicit grant per plugin, with a visible indicator while it is in use.
  • Budgets. Plugins get time and memory limits; one that stalls is suspended with a notice naming it, rather than freezing the app.
  • Themes are CSS variables plus optional layout slots — no code, no permissions.
  • Distribution through a reviewed registry with signed releases, plus sideloading for anyone who wants it.

A compatibility shim for another product's plugin API is explicitly not promised. Instead, phase 4 ships a porting guide and pays a small bounty for the twenty most-wanted community plugins.

16 · Backend and infrastructure

Services

  • Identity: accounts, passkeys, sessions, devices
  • Sync relay: document logs, presence, fan-out
  • Blobs: content-addressed, presigned uploads
  • Push: FCM, APNs, Web Push
  • Sharing: public links, permissions, revocation
  • Billing, admin, abuse handling

Foundations

  • Rust services, one repository, one deploy pipeline
  • Postgres for metadata; Redis for presence and rate limits
  • S3-compatible object storage with versioning
  • OpenTelemetry traces, metrics, structured logs
  • Infrastructure as code; staging mirrors production
  • Backups tested by restoring weekly, not by hoping

Service objectives: relay availability 99.9%; an update accepted and fanned out at the 95th percentile in under 400 ms within a region; zero tolerance for a lost acknowledged update, alerted on directly. Self-hosting is a first-class target from phase 2 — a compose file, one binary, documented upgrade path — because it is a large part of why this audience distrusts cloud note apps.

Files first, APIs second

The default importer for every source is a file the user already has or can request in a few clicks. File import works offline, needs no OAuth screen, survives no rate limit, and does not depend on a vendor keeping an endpoint alive. API connectors are the convenience layer added in phase 4 on top of the same converters.

Rules every importer follows

  • Nothing is overwritten. An import lands in a dated folder of its own. Merging into existing notes is a separate, explicit action afterwards.
  • Originals are kept verbatim. The source JSON, HTML or ENEX is stored beside the converted markdown in _original/. Conversion is lossy; the evidence should not be.
  • A fidelity report, always. At the end the user gets a plain list of what did not convert cleanly, each line linking to the note and the original. No silent degradation.
  • Resumable and idempotent. A large Notion workspace at three requests per second is an hours-long crawl that will fail partway. Checkpoint after every page, re-run safely, never duplicate.
  • Attachments are downloaded during the crawl, not linked. Notion's file URLs are signed and expire in about an hour, and Graph's behave similarly — a link stored today is dead tomorrow.
  • Backoff is a feature. Respect Retry-After, expect throttling from Graph on long exports, and show honest progress rather than a spinner.
  • A frozen test corpus. A few hundred real exported notes covering the awkward cases live in continuous integration, and every importer change is diffed against expected output.
The one that will hurt

Handwriting. Keep drawings arrive as flat images, OneNote ink is partially exportable at best, and neither gives you the pressure and tilt data that makes ink feel alive in the canvas. Imported handwriting will be a picture of a note, not an editable stroke set. Say so in the import screen rather than letting people discover it later.

Build

Months 3–5 · milestone M1 · internal alpha

Build

  • Block editor with markdown, tasks, code, images, links and backlinks.
  • Local store, file watcher, SQLite index, instant search, command bar.
  • Desktop shell for Linux and Windows with a folder picker and multi-window support.
  • Board view with colored cards, in-app pinning, checklists.

Phase 2 — It is on your phone, and it is the same notes

Months 5–8 · milestone M2 · closed alpha, roughly 100 users

Build

  • Identity service, passkeys, devices, sessions. Account-level encryption.
  • Sync relay, update log, snapshots, presence, resumable attachment transfer, LAN peer sync.
  • Android app with widget, quick-settings tile, share target and notification capture.
  • Desktop quick-capture hotkey and always-on-top sticky windows.
  • Self-hosting compose file and documentation.
Exit test: a week-long chaos run — devices going offline mid-edit, clocks skewed, files edited by an external editor — ends with zero lost acknowledged updates and zero corrupted files. Capture to typed text under 400 ms.

Phase 3 — Structure and the canvas

Months 8–12 · milestone M3 · closed beta, roughly 1,000 users

Build

  • Collection schemas, typed properties, relations, rollups, a basic formula set, the repair queue.
  • Table, board, calendar, gallery and list views with saved filters and sorts.
  • Infinite canvas: shapes, connectors, frames, note cards as transclusions.
  • Ink with pressure and tilt, palm rejection, shape recognition; OneNote-style freeform pages.
  • Mermaid blocks and Excalidraw-compatible drawings; SVG and PDF export.
  • Android stylus tuning on real tablets.
Exit test: the performance budget is met on reference hardware, and beta users can move a Notion database and an Obsidian vault in and keep working without touching the old apps for two weeks.

Phase 4 — Vault, plugins, and the browser

Months 12–16 · milestone M4 · open beta

Build

  • Vault: passphrase, per-document keys, biometric unlock, auto-lock, recovery phrase, local encrypted index.
  • External security review and a published threat model.
  • Plugin runtime, capability manifests, budgets, signed registry, porting guide and bounties.
  • Web client on the WASM core, with the vault read-only.
  • Sharing by link with permissions and revocation; importers for Keep, Notion, Obsidian, OneNote and Evernote.
Exit test: the security review closes with no unresolved high-severity findings, and ten third-party plugins run without a crash or a permission escape.

Phase 5 — Apple platforms and 1.0

Months 15–18 · milestone M5 · public launch

Build

  • macOS shell with menu bar capture, notarisation, and desktop stickies.
  • iOS and iPadOS app with widgets, share extension and Apple Pencil support.
  • App Store and Play Store submissions, with review lead time budgeted twice.
  • Accessibility audit, localisation of the first five languages, documentation, pricing and billing.
  • Performance and stability hardening; on-call rotation and incident runbooks.
Exit test: crash-free sessions above 99.5% across all platforms for three consecutive weeks, and every 1.0 quality number met on reference hardware.
